How this documentation is organised#

It follows Diátaxis, which sorts documentation by what the reader is doing rather than by what the software is made of. A tutorial and a how-to guide both contain steps, but they are not the same document and should never be written as if they were: one serves study, the other serves work.

Action — practical stepsCognition — theoretical knowledge
Study — acquisitionTutorials. We do it together, and you learn by getting somewhere.Explanation. Why it is like this, and what was rejected.
Work — applicationHow-to guides. You already have a goal; here are the steps.Reference. What is true, stated so you can check it.

A tutorial and a how-to guide are both numbered steps, and they sit in different rows. That distinction is the one the framework turns on: a tutorial may not pause to discuss alternatives, and a how-to guide may not stop to teach.

Two of these were already strong here and two were empty. The reference and the explanation existed as ARCHITECTURE.md and docs/architecture/; the tutorials did not exist at all, and the how-to material was scattered across a README, a contributor file and a section of the module reference. Writing the missing halves was most of the work behind this site.

Nothing here is a copy. Every page renders a Markdown file that lives in the repository and is readable on its own, and the build fails if a cross-reference goes stale. ARCHITECTURE.md remains the system of record for every measured number; this site lowers it into two views — the design and the evidence log — in the same spirit as the renderer lowering a scene.

If you are new#

Start with Render your first image, then Watch a scene lower — that second one takes a few seconds, needs no GPU, and carries the idea the whole project is built on. If you would rather read than run, the interactive explainer walks from what is a reservoir to the four reuse defects this design made measurable.

If you are here to change the estimator#

Read Invariants and the relevant entries of the evidence log first — they will save you rediscovering a dead end that is already written down — then follow Measure a change for bias. Low variance is not correctness: a biased ReSTIR produces a clean, beautiful, wrong image, so changes there are argued with numbers rather than renders.
