Architecture

The design in depth: the two load-bearing ideas, the layers, and what is deliberately out of scope.

Source: ARCHITECTURE.mdunderstanding-oriented

A Direct-Lighting → RIS → ReSTIR DI path tracer built as a lowering pipeline: a symbolic scene description is transformed through progressively more concrete representations until it reaches executable kernels, and every intermediate is a first-class, inspectable artifact.

  cornell.edn                        text
      │  read          spanned s-expression forms
      ▼
  forms                              pt/dsl/reader.py
      │  macro-expand  user + builtin macros, spans preserved
      ▼
  forms                              pt/dsl/macro.py
      │  analyze       shape checking, per-field source spans
      ▼
  SceneAST            level 2        pt/dsl/ast.py
      │  elaborate     resolve · default · normalize · stitch · expand
      ▼
  SemanticIR          level 2.5      pt/dsl/ir.py
      │  declare       passes state their reads and writes
      ▼
  RawGraph            level 3        pt/graph/builder.py
      │  compile       order · cull · lifetimes · alias · guard
      ▼
  ExecutionPlan       level 4        pt/graph/plan.py
      │  execute       walk a schedule; no reasoning
      ▼
  Taichi kernels                     pt/kernels/
      │  cook
      ▼
  artifacts: radiance, AOVs, reservoirs, path trees

Each arrow is a pure transform. Any level can be dumped and diffed (pt edn, pt describe, pt dump).

The two load-bearing ideas#

1. Functional core, imperative shell — with the boundary in the right place.

pt/core/ is genuinely pure: no I/O, no globals, no mutation of inputs, f64 throughout. pt/shell/ owns threads, windows, input and files. But the Taichi kernels in pt/kernels/ mutate fields freely, because pretending otherwise would make them slow and awkward for no benefit.

The contract lives at the pass boundary instead: a pass may only touch resources it declared, and its declared outputs are a deterministic function of its declared inputs, params and seed. graph/compile.py enforces this by handing each pass a scoped CompileContext — reaching for an undeclared buffer raises when the graph is built, not on some later frame.

2. Counter-based RNG is what makes everything else possible.

Every stochastic decision is a pure hash of (pixel, sample, bounce, dim, seed). ti.random() is banned. Three consequences the design leans on hard:

  • the pure reference and the Taichi kernel draw the same numbers, so they can be diffed per sample rather than merely statistically;
  • clicking a pixel re-derives the path that was actually traced, so the inspector shows evidence rather than a plausible re-roll;
  • the worker can be interrupted and restarted at any point and still produce identical images, which is what makes camera motion cheap.

The dimension layout in core/rng.py is a documented contract with kernels/_common.py, and it allocates one stream per path vertex: vertex 0 keeps BOUNCE_SHADE, so a two-bounce render draws exactly the numbers a one-bounce render draws at its first vertex, and deeper vertices get ids of their own rather than an offset inside the candidate block — whose width is M * CAND_STRIDE for a runtime M, so any fixed offset would collide for some M and the collision would be invisible. Two correlated draws look exactly like two independent ones.

Layers#

pt/dsl/ — the front end#

EDN surface syntax with source spans threaded through every stage, so a semantic error found three phases later still underlines the exact keyword:

error[UNKNOWN_MATERIAL]: geometry :s_left references unknown material :m_wihte
  --> cornell.edn:41:74
   |
41 |    {:id :s_left :prim :sphere :center [185 120 169] :material :m_wihte}
   |                                                               ^^^^^^^^
  help: did you mean :m_white?

Validation is layered, not duplicated: analyze catches shape errors (is this a 3-vector? is :radius present?), elaborate catches semantic ones (does that material exist? is this light bound to an infinite plane?). Errors are collected and raised once, so four typos report four errors.

The elaborate pass does five jobs, kept mentally separate because they fail differently: resolve names to dense indices, default omitted fields, normalize derived quantities (camera basis, quad normals and areas), stitch lights to their geometry in both directions, and expand the integrator keyword into the flags the graph builder switches on.

:type (which transport) and :light-sampling (how it is sampled) are separate axes, and elaborate is the only place that knows which of their combinations mean anything. :direct-lighting requires :max-bounces 1; :global-illumination requires two or more; multi-bounce resampling is refused there, with a span, rather than surfacing as a graph-build failure or — far worse — as a render that quietly traces fewer bounces than it was asked for. Those two constraints are each other's converse, which is what lets the depth be the single source of truth: writer.py re-derives :type from :max-bounces instead of the IR carrying a second copy that could disagree with the first.

Index assignment is source-ordered, never hash- or alphabetical-ordered. That is load-bearing: it makes every downstream buffer layout, RNG stream and ReSTIR reservoir index a deterministic function of the source text.

pt/core/ — the pure reference#

A complete, readable, obviously-correct implementation of the whole renderer in f64 Python. It is slow, and that is the accepted price of being checkable. It serves three roles at once: the correctness oracle the kernels are diffed against, the engine behind click-to-inspect, and the thing simple enough to validate against closed-form ground truth.

integrators/gi_uniform.py is the multi-bounce member of that family: NEE at every path vertex, cosine-weighted BSDF sampling between them, and Le added at the primary hit only. It shares _shared.nee_sample with di_uniform, so "GI at one bounce is direct lighting" is true through the same function calls rather than by careful transcription — the two agree bit for bit, not in the mean.

reservoir.py is where ReSTIR is either right or silently wrong, so the three combination rules (naive, mis, pairwise-mis) are spelled out there rather than folded into a helper.

That file holds one copy of the reuse algebra for two payloads. A ReuseDomain is the whole difference between reusing a light sample and reusing a path: a target function, and a shift mapping's Jacobian. Everything else — Chao's update, the three weightings, the partition-of-unity argument, the rule that a stream which found nothing still carries its confidence — is payload-agnostic and must stay that way; a second copy is where a fix would reach one estimator and not the other. The payloads are separate types (LightSample, PathSample) and separate device structs, so the statements that a light reservoir's Jacobian is 1 because it stores a world-space point stay true verbatim rather than becoming conditionally true.

The seam is testable before the second payload uses it: injecting a deliberately wrong Jacobian must move the answer, while DI_DOMAIN's must be exactly 1 — which is how a refactor that quietly dropped the factor would be caught, since every DI test would otherwise still pass.

reconnect.py is the path payload's half of that: the shift mapping and its Jacobian. Connecting a stored vertex to a new shading point is an exact re-derivation, as it is for a light sample — a point does not change when you look at it from elsewhere — so the only real content is the change of measure:

dw = cos_2 dA(x2) / d^2          =>   J(r -> q) = (cos_q / d_q^2) * (d_r^2 / cos_r)

with both cosines at x2. Three plausible-looking mistakes, each producing a clean and wrong image, are worth naming because the code is written to make them hard: using the cosine at x1 (that one belongs to the integrand, not the change of variables, and reads as a shading error); inverting the ratio (a contribution weight is a reciprocal density, so it takes the forward Jacobian — backwards is a factor of (d/d')^4 that does not shrink with sample count); and clamping instead of rejecting. J diverges as cos_r -> 0, which is a real firefly source, but clamping it silently rewrites the estimator, whereas refusing the reconnection does not — provided the refusal also removes that stream from the MIS denominator, which it does because both paths call the same function.

Reconnection reuses the stored radiance as if it were view-independent. For a Lambertian x2 that is exact, and every material here is Lambertian; it is also the first thing a glossy BSDF breaks, which would need the suffix re-evaluated rather than merely re-weighted. This is the same view-independence argument the temporal-reprojection finding already leans on.

pt/graph/ — the render graph#

Frostbite's declare → compile → execute, with SSA-versioned virtual resources. Compile runs rarely and does all the reasoning; execute runs every frame and does none.

assemble_di_graph is the single place the DL → RIS → ReSTIR progression is expressed. Uniform and RIS are one shade node; ReSTIR expands into InitialAndTemporal → Spatial → Resolve with persistent reservoirs. Everything else in the graph is identical across all three.

Path depth is a second axis through the same swap point. Uniform sampling past one bounce is ShadeGI[uniform], declaring the same reads, the same writes and the same dirty domains as ShadeDI[uniform] — one node changes and nothing else does. Depth is a compile-time parameter, in the same class as the strategy and the resolution, because it changes the pass's RNG footprint; the graph refuses max_bounces > 1 for :ris and :restir-di, which resample light samples and so say nothing about a second bounce.

ReSTIR GI is not a fourth graph. ReSTIR.GI.* declares the same three passes over the same three persistent buffers with the same reads, writes and dirty domains as ReSTIR.*; only the reservoir's kind and the kernels differ. That is the graph-level statement of the claim core/reservoir.py makes about the algebra, and tests/test_graph.py asserts it pass by pass rather than leaving it as a comment that could quietly stop being true.

dirty_steps gives selective re-cooking for free: dragging the exposure slider re-runs exactly one pass and keeps every accumulated sample.

pt/kernels/ — the Taichi execute layer#

One rule beyond the RNG: anything the shell can change without recompiling is a kernel argument, never a compile-time capture. Camera, exposure, AOV selection, sample index and bias mode all arrive per launch. A closure holding them would silently render a stale world — the failure mode that makes an exposure slider appear inert.

pt/shell/ — the imperative shell#

DearPyGui on the main thread, Taichi on a worker thread, communicating through a command queue and a single-slot frame queue. The single slot is the double buffer: the worker replaces a stale frame rather than blocking.

Click-to-inspect runs the pure core on the UI thread — no Taichi call ever happens there, including for inspection.

validation/ — the correctness harness#

The chain of trust:

analytic (closed form)  ->  validates uniform MC (1 bounce)  ->  validates RIS and ReSTIR DI
      |
      +->  quadrature  ->  validates uniform MC (2 bounces)  ->  validates ReSTIR GI

analytic.py deliberately re-implements its own vector math rather than importing pt.core.vecmath. An anchor that shared code with the thing it validates could be corrupted by the same bug and pass anyway.

One bounce further there is no closed form, so indirect.py anchors the indirect term with a quadrature: the same integral as a Riemann sum over (theta, phi) and over the light's area. It borrows intersect_scene — an independent ray tracer would be a second renderer — and nothing else, and its own inner integral is checked against the closed form so a failure says which side is wrong.

gi.py is where the last arrow is actually made, and it exists because none of the image statistics above can see a GI estimator. The indirect term is ~11% of the Cornell box, so a defect in the only quantity ReSTIR GI is responsible for arrives at a whole-image test divided by nine — the 25% spatial-reuse bias in the findings below read 0.9953 on total energy. Every GI statement is therefore made about render(2 bounces) - render(1 bounce), a subtraction that is exact rather than statistical because vertex 0 draws the same RNG dimensions either way, and which is valid for exactly the two strategies that share those draws — :uniform and :restir-gi. require_shared_direct_term refuses the rest rather than returning a number nobody can interpret.

Two consequences shape the rest of the module. Reuse rows discard a warm-up before measuring, because a ReSTIR accumulation from frame 0 averages in the path tracer it starts as. And the headline statistic is energy, not MSE: on a term this small the MSE-excess verdict stays inside its margin while the energy ratio resolves the same defect at tens of sigma. Both are measured, in "Findings worth keeping".

flip.py answers the one question none of the above can phrase: would a person see it, and where. Every other statistic here is a number about radiance, and two of this project's recorded failures were cases where the number was fine and the image was not, or the reverse. FLIP (Andersson et al., HPG 2020) models a viewer alternating between two images, and is bounded per pixel — so unlike MSE, which a single firefly has been measured to own at 25000x the median, nothing can dominate it. It is emphatically not a bias detector: a converged biased estimator is perceptually smooth and scores well, which is the whole reason the energy and MSE sections still carry the verdicts. It ranks and it localizes.

Deliberately out of scope#

  • Triangle meshes and a BVH. They slot in behind intersect_scene without the estimator noticing; analytic primitives keep closed-form ground truth available, which is worth more here than geometric generality.

  • Motion vectors. Reprojection is implemented (:reproject true) but assumes a static scene: a shading point's previous screen position is found by projecting it through the previous camera, which is exact for geometry that has not moved and wrong for anything that has. Animated geometry would need a per-pixel motion vector instead, which is a change to the reprojection lookup and to nothing else — the MIS weighting already evaluates the temporal stream's target at whatever point it is handed.

  • A ReSTIR GI whose reuse is unbiased. The estimator is complete and the harness now points at it, which is how the empty-stream bug above was found and fixed. What remains is a measured, unexplained energy deficit when temporal and spatial reuse are both enabled: each pass alone lands within 0.7% of the converged reference on the indirect term, and together they read 0.949. The deficit scales cleanly with how much confidence the temporal pass accumulates —

    m_cap12520
    indirect energy0.9840.9780.9660.949

    — which points at the same question the asymmetry above raises: what an accumulated M should mean when the reservoir carrying it holds no sample, and what a spatial neighbour should do with a neighbour's accumulated confidence. The two rules that are right for fresh streams and for a pixel's own history do not obviously compose. Until that is resolved, ReSTIR GI here is unbiased in each reuse mechanism separately and measurably dark with both, and it should not be described as validated.

    What holds it up in the meantime is the identity: at M=1 with reuse disabled the estimator is the two-bounce uniform path tracer, drawing the same numbers, so the target function, the contribution weight and the choice of measure are all checked per sample against something already anchored to a quadrature. That is the GI analogue of "ReSTIR with no reuse equals RIS", and it earned its keep twice before any statistical test ran — see the two epsilon findings above, neither of which an image or an invariant test would have shown.

  • Real transient memory aliasing. Lifetimes and slot assignment are computed and asserted, but Taichi allocates a field per slot; the byte savings are a native-backend concern. The interface is honest now so the optimization is a backend detail later.

Taichi constraints worth knowing#

Four behaviours that are easy to violate and produce failures that say nothing about the actual cause. All are enforced or worked around in kernels/runtime.py and engine.py.

ConstraintWhat it looks like when violated
ti.init() binds the LLVM context to the calling thread; only that thread may allocate fields. Launching kernels and to_numpy() from other threads is fine.Assertion failure: std::this_thread::get_id() == main_thread_id_ from llvm_context.cpp — no mention of threads owning fields
Field materialization is deferred until first access, so allocating on the right thread is not enough — it must also be touched there.The same assertion, but at first render rather than at construction, so building appears to have succeeded
The default root FieldsBuilder is finalized on first materialization; no field can be created afterwards.TaichiRuntimeError: FieldsBuilder finalized when a second engine is built
Writing to a field forces materialization, which is illegal while a caller-owned FieldsBuilder is still open.Field builder ... is not finalized raised from inside an innocuous-looking data upload
Any kernel launch validates that no builder is open — including one launched by another thread.A rebuild on the main thread kills the render worker mid-frame with a bare TaichiRuntimeError

The resulting shape: each Engine owns a ti.FieldsBuilder, allocates every field into it, finalizes it, then uploads scene data, then reads each field once to force materialization — all on the main thread. The render worker receives a finished engine and only runs it.

Rebuilding adds one more step. Because an open builder invalidates kernel launches anywhere, the worker is parked — blocked until it confirms it is idle — before allocation begins, and the old engine's field tree is released only once the worker has adopted the replacement. Merely asking the worker to freeze is not enough; the rebuild has to know it has actually stopped.

Two more, unrelated to threading:

  • from __future__ import annotations breaks Taichi. PEP 563 turns annotations into strings, and Taichi reads @ti.kernel / @ti.func argument annotations as live type objects. Every module under pt/kernels/ carries a note about this.
  • ti.template() does not thread a scalar through a @ti.func. It passes fields by reference, not local scalars, so a stateful RNG whose counter is "advanced" by a callee silently returns the same number every draw.
