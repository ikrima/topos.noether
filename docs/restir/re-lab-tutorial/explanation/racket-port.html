What the Racket port showed

Status of all eight steps, and the arguments the port settled by being written.

Source: port/racket/README.mdunderstanding-oriented

A reimplementation of this project's thinking layers — the DSL front end, the render graph, and the pure reference estimator — in Racket, so that the estimator becomes something you write rather than something hardcoded.

The plan, the essential-vs-incidental split, and the order of work are in docs/architecture/porting-to-racket.md. The semantics being reproduced are in docs/architecture/semantics.md.

Run the tests#

raco test port/racket             # everything
port/racket/test/mutations.sh     # break the port on purpose, ~3 min

70 mutations are caught and 6 are documented as not caught, with reasons.

No installation needed — the tests require by relative path. To make (require restir/rng) work from anywhere:

raco pkg install --link port/racket

What step 2 showed#

pt/dsl/reader.py is 283 hand-written lines — a tokenizer, a recursive-descent parser, and a Span record threaded through every node. edn.rkt replaces it with six lines of readtable configuration, because EDN is s-expressions and read-syntax attaches source, line, column and span to every node for free. Three parameters arrange the differences: #%brackets/#%braces tags to keep the vector/map distinction, and a readtable entry making , contribute nothing.

That is the port's whole argument, delivered: the Python had to rebuild by hand exactly what the host already provides — and the spans it gets back are better, because they are real syntax objects that survive macro expansion.

The rest of the front end does not evaporate. elaborate.rkt is 490 lines against the Python's 387, because its five jobs — resolve, default, normalize, stitch, expand — are domain logic, not parsing. One thing deliberately does not use the host's machinery: raise-syntax-error reports the first problem, while a scene with four mistakes should report four, so diagnostics accumulate explicitly and raise once.

What step 3 showed#

Nothing evaporates here. pt/core/'s geometry, camera, lights and shading are domain arithmetic, and the Racket is within a few lines of the Python file for file — which is the useful negative result: the port's argument is about the front end and the estimator, not about arithmetic, and this step is where you would notice if that claim were being oversold.

What it did produce is a stronger acceptance test than expected. test/geometry-conformance.rkt compares 55,184 values against conformance/geometry.json — per ray for intersect-scene, per (pixel, sample) for di-uniform, over four scenes — and every one of them is bit-identical, not within tolerance. The suite allows a 1e-12 relative tolerance for the three libm calls in the path (tan in the camera basis, sqrt in every length, sin/cos in the sphere light); measured, it is never used. The tolerance stays for a different platform's libm, but the practical reading is that a port needing a loose tolerance has a structural difference rather than a rounding one.

Two things are worth carrying into step 4:

  • (values ...) where the Python returns a tuple. eval-contribution returns four values and nee-sample returns four; define-values at every call site is more honest than a struct, because these are genuinely positional results with no independent identity.
  • The fixture's sections are ordered by how a failure propagates. A bad shadow epsilon leaves rays clean and fails from occlusion on; a dropped light-selection probability leaves occlusion's geometry clean and fails light-samples. Checking only the final radiance would collapse every defect into "the image is wrong", which is exactly the diagnostic position this project spent the most effort escaping.

What mutation testing found that the fixture did not#

The step-3 fixture passed on its first run. Breaking the port on purpose — 23 edits, test/mutations.sh — found two defects it could not see at all, and both were about reachability rather than arithmetic:

  • EPS is unreachable through a render. Every ray a scene traces starts at the camera or at a shading point already offset by shadow-epsilon, which is ten times larger. Deleting the guard that stops a ray re-hitting its own surface changed no pixel of any scene.
  • Every quad in every bundled scene is a rectangle. intersect-quad solves against a 2×2 Gram matrix whose off-diagonal is dot(u, v); with rectangles that is exactly zero and the terms carrying it vanish. Corrupting one is a no-op on all nine scenes — and even a sheared quad hides it unless the corrupted (s, r) lands outside the unit square while the correct one is inside, since otherwise the same t comes back.

Both are now pinned by calling the intersection routines directly, and coverage_scene.edn carries a sheared quad, a sphere light, a two-sided light and a plane occluder — four branches no shipped scene reaches.

Twenty mutations are caught. Three are documented as not caught, which is the part worth keeping: emitted-radiance's sidedness branch is unreachable once intersect-scene face-forwards the normal (the smallest dot(n, wo) over the coverage scene's emitter hits is 0.050), bsdf-eval's dispatch is dead until a second material exists, and vlerp has no caller in the ported surface at all.

What step 4 found#

The reuse algebra ported cleanly — reservoir.rkt is 300 lines against the Python's 372, and test/reservoir-conformance.rkt compares 53,311 values across five configurations, including the whole three-pass frame loop per pixel per frame, all bit-identical. What is worth reading is the three things that were not clean.

CPython's sum() over floats is not a left fold. Since 3.12 it is Neumaier compensated, so sum([0.1]*10) is exactly 1.0 where (apply + ...) gives 0.9999999999999999. mis_weights_at uses it for the balance heuristic's denominator, and the disagreement appears only at three or more live streams — compensated and naive summation coincide for two — so it is invisible in the two-stream temporal merge and shows up under spatial reuse. vecmath.rkt implements Neumaier explicitly. Two consequences worth carrying: the accuracy is wanted on its own terms, since that denominator sums targets spanning orders of magnitude; and a 1e-12 tolerance cannot see a one-ulp defect, so both conformance suites now allow the tolerance and separately assert exactness.

Python's negative list indexing has no equivalent here, and that is a feature. The first fixture ran generate_candidates at neighbour pixels whose primary ray had missed, reaching scene.materials[-1] — which in Python quietly returns the last material and produces a plausible number. Racket raised. The fix was to the fixture, not to the port: the renderer never runs initial RIS at a miss, so pinning the Python's answer there would have frozen an accident into the contract.

PAIRWISE-MIS is not unconditionally a partition of unity. Running Σᵢ mᵢ(y) = 1 over randomly generated stream configurations — which is what step 4's acceptance actually asks for — showed the pairwise rule summing to k_valid/k whenever the canonical stream is blind to y and some neighbour is too, because that pair is 0/0, is skipped, and contributes to neither weight. On a real bias_demo render 3.8% of the weighted samples fall short, by 0.51 on average. It changes no pixel, because b = 0 implies the merge's own p̂_q(y) is 0 and the contribution was zero regardless — but only as long as streams[0].hit is the merge target, which is true at every call site and enforced at none. test/mis-properties.rkt pins the counterexample, the measurement and the invariant. The Python's own test cannot see it: four streams on one wall lit by one light means every density is positive and the precondition is never probed.

What step 5 found#

Reconnection is the one genuinely new piece of mathematics in path reuse, and it ported without incident: 36,116 values against conformance/reconnect.json, all bit-identical, including the GI frame loop with its pre-spatial history roll. What step 5 did produce is a correction to this project's own documentation.

"ReSTIR GI at M=1 with reuse off is the two-bounce path tracer" is not true, and it was written in five places. What the gi-cand-dim alias buys is that the two draw the same numbers, so they can be compared per sample rather than statistically. Their outputs still differ: the bounce ray leaves from x1 + eps·n, so the vertex it finds is not exactly on the ray from x1 — the path tracer evaluates at the direction it sampled, reuse re-derives the direction from the stored vertex, and the two differ by about eps/d. Measured at 20×20 on cornell_restir_gi: 103 of 185 samples agree bit for bit, one exceeds 1e-3, the worst is 7.3e-3, totals agree to 2.7e-5.

tests/test_core.py::TestGiRestirIdentity had it right and asserts the residual's shape rather than a tolerance. The docstrings and the porting spec did not, and the wording invites exactly the equality assertion that then fails with nothing attached to explain it — which is what happened here, in the fixture generator, before the measurement replaced the assumption. All five now say what the alias actually buys.

Two things about how the fixture is built are worth carrying to step 6:

  • The Jacobian's laws are hand-computed, not derived from the implementation. reconnect reads nothing from the scene, so J = 4, not 1/4 can be written down independently and the fixture carries the derived answer alongside the Python's. Reciprocity and the identity case both hold for an inverted ratio, so neither can catch the error worth catching.
  • read-json maps JSON null to 'null, which is truthy. The fixture records an absent path suffix as null, and (and ye #t) cheerfully reported every one of them as present. Seventeen candidates that should have failed passed instead — a checker bug of exactly the kind the mutation harness exists to catch, found here by the fixture disagreeing.

What step 6 found#

The graph is the one layer with no arithmetic in it, so the acceptance is different in kind: describe compared character for character across all nine bundled scenes plus four variants, and dirty-steps over all 32 subsets of the five domains rather than the five. 2,723 comparisons, all matching.

Character-for-character turns out to be the strongest single assertion in the port. describe prints slot numbers, so that one string transitively pins declaration order, the topological tie-break, culling, the lifetime intervals and the greedy colouring's first-fit rule — five things with no numeric output of their own. Every one of them has a mutation, and all five are caught by the string alone.

Two and a half of the five compile stages are dead code on every shipped scene. Measured across all thirteen configurations: nothing is ever culled, nothing is ever aliased (n_physical equals the resource count in all thirteen), and the topological sort is the identity, because assemble-di-graph already declares passes in dependency order. A port can get all of them wrong and reproduce every real plan exactly — which is the step-3 lesson in its sharpest form, on a render graph with exactly one client.

Five synthetic graphs fix that, and the fifth is the interesting one:

graphreaches
dead_passstage C — a pass whose only output nobody reads
aliasingstage D's interval colouring, n_physical < resources
two_free_slotsfirst-fit vs last-fit, which agree unless two slots are free at once
diamondstage B's tie-break, declared sink-first so the sort must reorder
persistent_historythe v0 read exemption, isolated from ReSTIR

two_free_slots exists because swapping for/first for for/last in slot assignment changed nothing on aliasing — with one free slot in flight every allocation rule picks the same slot. The generator now asserts that culling and aliasing are dead on the real scenes, so the synthetic graphs' premise fails loudly if the builder ever changes.

One Racket note worth carrying: for*/list nests its clauses, so ([p (in-list passes)] [pi (in-naturals)]) iterates the naturals to infinity inside each pass. for/list binds them in parallel. That hung the first run of stage A, and it is the kind of mistake the Python's enumerate cannot make.

What step 7 found#

The frame loop itself ported without incident — render.rkt grew from 155 lines to 300, campath.rkt is 80, and test/frameloop-conformance.rkt compares 26,128 values against conformance/frameloop.json, every float bit-identical. The energy table reproduces to the last place as well, which is worth dwelling on: it is a statistic, and step 1's per-sample discipline makes even a mean an exact claim rather than an error bar.

mis1.00000.95480.95740.9156
naive1.00000.95480.91000.8833

The digits are not §10's — those were the f32 kernels at 128px against a 4096-spp reference, these are the f64 reference path at 48px. The shape is, and the shape is the claim: exact without reuse, temporal-only weighting-insensitive to nine decimals, and MIS recovering part of what 1/M loses spatially and only part. The deficit is still open, and the port reproduces it.

What the step actually turned up is four things, and the first is about the Python.

The oracle could not express its own measurement protocol. validation/gi.py is built on Engine.render(warmup) + reset_accumulation(), which clears the image, keeps the reservoirs and sets spp_index back to 0 — and the reference twin in pt/core/render.py had no way to say that. It only had spp, so the best a measurement could do was slice frames off the front, leaving the measured frames on samples warmup … warmup+spp-1 while the subtrahend renders 0 … spp-1. The direct term then stops cancelling per sample and starts averaging away instead. Measured: the no-reuse identity, which is supposed to be the uniform control sample for sample, read 0.9989 against a control of 1.0099 — 0.011 apart, on a statistic whose whole job is to resolve a few percent. With the rewind they agree to 3e-4, which is finding 24's eps/d residual and nothing else. warmup= is now a parameter of render_reference, additive and default-off; CLAUDE.md's "every estimator lives twice" was quietly false here, because only one of the twins could describe the experiment.

NumPy's mean is pairwise-summed. This is the third summation convention the port has had to reconcile, after CPython's compensated sum() (step 4) and the naive fold. Over the 6,912 floats of a 48px frame the pairwise and left-fold means differ by ~1e-12 relative — which is exactly REL-TOL, close enough to look like a rounding question and far enough to start failing when the resolution changes. The fixture and the port both use Neumaier, the one convention the two languages genuinely share; validation/gi.py keeps np.mean, because there the question is three decimals rather than a bit-for-bit diff.

The parameter that makes reprojection measurable is resolution-dependent, and the fixture nearly froze that in. DEFAULT_MAGNIFY = 20 is tuned for 128px; at the fixture's 16px it pulls the history camera back until the previous frame's view of the scene is smaller than one pixel, so every shading point projects into one sub-pixel blob or off the frame. The history map comes back all -1 — and it matches itself perfectly, so the section would have passed against a port with no reprojection whatsoever. Measured: 0 of 1,536 pixel-frames accepted, on both scenes. At 3.0 the same 1,536 split into 866 off-screen, 272 rejected by the disocclusion gate, 398 accepted and 13 mapping to their own pixel. The counts are in the fixture and asserted as coverage, separately from matching.

Two more mutations are documented as uncatchable, both by measurement rather than by shrug. focus-distance's two compensated sums are unreachable as a defect: the 17-prim centroid of reproject_demo, the 8-prim centroid of cornell_restir_gi, coverage_scene, and the three-term dot product in all of them are bit-identical under compensated and naive summation on every axis, because the prim origins are coordinates whose partial sums stay exactly representable. And the per-frame camera never reaches the scene — with-camera is threaded through the loop exactly as the Python threads it, but nothing downstream of the primary ray reads scene.camera, so substituting it is dead on the ported surface. Both are kept because the Python has them and the two must not drift, and the second stops being dead the moment anything screen-space appears downstream.

One thing the port declined to improve: estimate_pixels refuses RESTIR_DI because reuse couples pixels, and does not refuse RESTIR_GI, which couples them exactly as much and falls through to direct-lighting RIS — an estimator of a different quantity. The port reproduces the oracle and the test pins both branches. That gap is the oracle's to fix, and fixing it in the port first would only have hidden it.

What step 8 delivered#

Steps 4–7 ported the estimator faithfully and hardcoded it: the payload was a struct literal, the weighting rule a branch of a cond on an integer, the RNG layout a page of constants, and which reservoir rolled into the history an (if gi? …) three-quarters of the way down a loop. Step 8 makes all four declarations. estimator.rkt is the language; estimators.rkt is written in it, with #lang s-exp "estimator.rkt", and is 80 lines of which the load-bearing part is this:

(define-frame-loop restir-gi
  #:initial+temporal gi-initial-and-temporal
  #:spatial          gi-spatial-reuse
  #:resolve          gi-resolve-pixel
  #:history          'temporal)   ; finding 23

Finding 23 is that last line, and the acceptance is that both branches reproduce their measured numbers. test/history-roll.rkt renders the estimator under each, sweeping m_cap — which is the signature that made the defect diagnosable, because m_cap was never the cause, only the knob setting how long a sample survives to be copied:

Both rows land within 0.03 of the recorded kernel measurement, which was taken at 96px in f32 under a different protocol. The shape is exact: the wrong roll falls monotonically in m_cap, the right one does not move. That second row is the decisive one — it holds every confidence fixed and moves only sample identity, which is what proved the defect was duplication rather than confidence accounting, the leading hypothesis and the wrong one.

Obligations became checkable, not just findings. test/mis-properties.rkt used to enumerate the three weighting rules by hand; it now derives them from the registry, so Σᵢ mᵢ(y) = 1 applies to whatever rules exist rather than to the three that happened to be there when it was written — and a rule registered without a stated law is an error rather than a vacuous pass. Each rule also declares whether it is a partition of unity, and a test checks that declaration against the law, so pairwise-mis's #:partition-of-unity #f is an assertion with a counterexample behind it instead of a paragraph of prose.

define-rng-layout earns its place by checking three things at expansion time that no amount of reading catches reliably: that every slot fits inside its block's stride (a slot past the stride lands on the next repetition, and since the repetition count is a runtime parameter that collides for some counts and not others); that two blocks sharing one bounce declare it, so the deliberate gi-cand/bsdf overlap is written down and an accidental one is a build error rather than two "independent" draws that are the same number; and that the declared alias (gi-cand-dim 0 U) = (bsdf-dim 0 U) actually holds. That last is what makes ReSTIR GI at M=1 comparable to the path tracer per sample, and reordering gi-cand's slots now stops the build instead of quietly ending the only exact cross-check the GI estimator has. All 2,240 frozen RNG vectors still reproduce, which is how the declaration is known to be the same layout.

Mutation testing found a hole in that alias check on its first run, which is the usual result and the reason the harness exists. The check compared dimension indices and never that the two blocks were in the same bounce — so moving gi-cand to another stream satisfied it perfectly while destroying the thing it protects, because hash4 folds the bounce into the key and equal indices in different streams are different draws. Fixed, and it is now the mutation that replaces the old arithmetic one on the hand-written accessor.

Nothing regressed: the whole refactor is behaviour-preserving against every per-sample fixture from steps 1–7.

Why the RNG first, and why it is not reorderable#

Every later verification in the port is a per-sample diff against the Python, and a per-sample diff requires identical draws. Until rand1 matches bit for bit, nothing downstream can be checked against anything except statistics — and statistics on ~11% of an image will not see a defect losing a sixth of the indirect term. That is not hypothetical; it is finding 26.

test/rng-conformance.rkt checks against docs/architecture/conformance/rng_vectors.json, 2,240 frozen vectors plus the dimension layout, and adds two things the table cannot express:

  • Injectivity over runtime-scaled blocks. Candidate and tap blocks are M-wide, so a fixed offset can collide for some M and not others. Checked over M ∈ (1, 2, 8, 32), because the collision is invisible in an image — two correlated draws look exactly like two independent ones.
  • The two deliberate invariants. (gi-cand-dim 0 U/V) aliasing (bsdf-dim 0 U/V), which is what makes ReSTIR GI at M=1 with reuse off draw the same numbers as the two-bounce uniform path tracer, so the two are comparable per sample; and (shade-bounce 0) = BOUNCE-SHADE, without which differencing against a one-bounce render stops being exact.

The suite is mutation-tested. An off-by-one in PCG-XSH, a wrong shift in pcg, a >>9 extraction, a folded-twice counter in hash4, a wrong stride, a broken alias, and a changed shade-bounce(0) are each caught.

Exactly one edit is not caught, and that is correct: dropping a u32 mask inside hash4 is a semantic no-op, because pcg masks its own input. Those masks are documentary — kept so the file reads line-for-line against pt/core/rng.py.

Notes for a reader coming from Python#

  • Racket integers are arbitrary precision. Every place the Python relied on 32-bit wraparound has to mask explicitly; that is what u32 is for.
  • arithmetic-shift shifts left on a positive count, right on a negative one. Python's x >> k is (arithmetic-shift x (- k)).
  • rand2 returns two values (define-values) rather than a tuple.
  • The comparison against the frozen uniforms is check-equal?, not a tolerance: (h >> 8) * 2^-24 is an integer below 2^24 scaled by a power of two, so it is exactly representable in IEEE 754 and every conforming implementation owes the same bits.
