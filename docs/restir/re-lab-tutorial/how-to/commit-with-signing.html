Commit with the signing agent

Two failures that look alike and have different fixes.

Source: docs/how-to/commit-with-signing.mdtask-oriented

Commits here are SSH-signed through the 1Password agent (op-ssh-sign). Two failures look alike and have different fixes. Your work stays staged either way, and --no-gpg-sign is never the answer.

Could not connect to socket. Is the agent running?#

Usually the agent is running fine and SSH_AUTH_SOCK is simply pointing somewhere else — a GNOME keyring, say. Point it at the right socket for the one command:

SSH_AUTH_SOCK=~/.1password/agent.sock git commit -m "…"

Signing stays on.

failed to fill whole buffer#

The agent is genuinely locked. Unlock it, then retry the commit. If you are driving this through an assistant, ask — there is nothing to work around.

git log --format=%G? prints N for everything#

That is not a signing failure, and it is true of old commits here too. There is no gpg.ssh.allowedSignersFile configured, so git cannot verify SSH signatures locally — it has no list of which keys to trust. Verification and signing are different operations.

To confirm a signature actually attached, inspect the object rather than asking git to verify it:

git cat-file commit HEAD | grep -c gpgsig

1 means the signature is there.

Never do this#

git commit --no-gpg-sign     # no

It produces a commit that looks fine locally and is unsigned in the history permanently. Both failures above are configuration problems with real fixes.
