Debug a single pixel

Path tree, candidate table, AOVs and the variance heatmap.

Source: docs/how-to/debug-a-single-pixel.mdtask-oriented

A pixel is too bright, too dark, or noisy where nothing else is. The shell can show you the estimator's actual working out for it.

.venv/bin/pt gui cornell_restir

Needs a display. Everything else in these guides runs headless.

Read the estimate as evidence#

Click the pixel in the Render window.

Path Tree shows the primary ray, the surface it hit, and every light-sample candidate drawn for that pixel at the current sample index — each with the light it sampled, cos_light, its target value p̂, its resampling weight w, its MIS weight m, its Jacobian, and whether it was occluded.

Candidates shows the same as a table. w / sum(w) is the selection probability. M is the effective sample count.

None of this is a replay. The path is re-derived from the same hash(pixel, sample, bounce, dimension, seed) the kernel used, so you are reading the sample that produced the pixel rather than a fresh draw from the same distribution. Click-to-inspect runs the pure Python core on the UI thread — no Taichi call ever happens there.

What to look for#

SymptomLook atLikely
Pixel far too brightthe chosen candidate's w and p̂a target function evaluating non-zero where the contribution is zero, or a Jacobian blowing up at a grazing angle
Pixel too dark, neighbours fineM, and whether streams were admitteda stream dropped instead of contributing its confidence — see empty streams
Noisy only near an edgeM on both sides of the edgethe geometric gate rejecting neighbours, which is usually correct behaviour
Fine still, wrong when the camera movestick temporal reprojection, then dragthe reprojection lookup, not the estimator

Step one sample at a time#

Drag spp cap in Controls. The primary ray jitters within the pixel and the light sample moves across the lamp — the Monte Carlo process, one draw at a time. If a pixel is wrong at one specific sample index and right at others, that index is the bug.

See it in space#

Debug 3D draws the same data geometrically: the render camera as a frustum, primary rays blue, rejected candidates dim, the survivor bright green, temporally reused samples pink, spatially borrowed ones orange with an arrow back to the pixel they came from.

For a suspected reuse problem this is the fastest view — a sample being borrowed from somewhere it should not be is obvious as a line in space and invisible in a table.

Look at the buffers instead of the image#

The AOV combo routes a cooked buffer straight to the display: normals, albedo, depth, reservoir weight. A pixel whose normal is wrong is a geometry bug, not an estimator bug, and this tells you which in one click.

variance heatmap shows where the renderer is still uncertain, which is often not where it looks noisiest.

Dump cooked artifacts writes everything to .npy for offline comparison — see Dump and diff an intermediate.

Compare estimators live#

strategy switches between uniform, RIS and ReSTIR DI. ReSTIR combine switches the reuse weighting between naive, mis and pairwise-mis.

If a pixel is wrong under all three weightings, the problem is not the weighting.

Headless alternative#

With no display, drive the pure reference directly — it is the same code the inspector runs:

.venv/bin/python -c "
from pt.dsl import load_scene_file, scene_path
from pt.core.pathtree import regenerate_path
ir = load_scene_file(scene_path('cornell_restir'))
tree = regenerate_path(ir, (128, 200), sample=0)
print(tree.kind, len(tree.children), 'children')
for c in tree.children[:3]:
    print(' ', c.kind, c.payload)
"
primary 33 children
  candidate {'candidate_id': 0, 'light': 0, 'p_light': (319.0006…, 548.7, 323.0381…), …}

With no live reservoir state this shows the initial RIS candidates only — temporal and spatial reuse are omitted, not approximated. The GUI says so in a note when it is in the same position. To inspect a pixel under warmed reuse you need a ReservoirProvider carrying real buffers, which is what the shell supplies from its render worker.
